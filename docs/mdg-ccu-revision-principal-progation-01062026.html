MDG - CCU - Proyecto - Revision principal progation 01062026

Recap de la revisión realizada el 01-06-2026 sobre Principal Propagation X.509 entre CF, Cloud Connector y SAP ABAP DS4 cliente 120.

Proyecto MDG Services Node.js Subaccount CCU-CF-DEV Backend DS4 / mandante 120 Evidencia: Trace.xlsx

Resumen Ejecutivo

Lo que ya funciona

La app en Cloud Foundry envía el JWT del usuario al Connectivity Proxy. Cloud Connector ya recibe identidad de usuario y genera un certificado X.509 de usuario.

Bloqueo principal

ABAP DS4 recibe el certificado reenviado en ssl_client_cert, pero lo descarta porque no confía en el intermediario que lo envía.

FSOLER

En el trace no aparece P000001 como CN de certificado. Para FSOLER, SCC está reenviando CN=fsoler@ccu.cl, que calza con la regla CERTRULE basada en correo.

Acción de Basis

Configurar trust del Cloud Connector/reverse proxy en ABAP, incluyendo certificado de sistema del SCC y parámetros ICM de reverse proxy confiable.

Flujo Revisado

Diagrama elaborado a partir de la revisión de logs y trace. No se encontraron capturas de pantalla como archivo local en el repositorio; se incorporan visuales embebidos y evidencia textual real.

Hallazgos de la Actividad

Hallazgo Evidencia Interpretación
Cloud Connector ya muestra usuario En monitor SCC se observaron requests con usuario, por ejemplo P000001. La identidad viaja desde IAS/CF hacia SCC. Esto es una mejora frente al estado anterior, donde el usuario aparecía vacío.
El token contiene usuario IAS/AD Log de CF con user_name=P000001 y email=fsoler@ccu.cl. P000001 puede ser el identificador IAS/AD. No necesariamente debe existir como usuario SAP si el mapping final es por correo.
SCC genera certificado de usuario con email Trace: subject="CN=fsoler@ccu.cl...". Para FSOLER, el certificado reenviado tiene el CN correcto para una CERTRULE que mapea CN a correo electrónico.
ABAP descarta el certificado reenviado Reject untrusted forwarded certificate y remove incoming ssl header. DS4 no confía en el intermediario/reverse proxy que envía ssl_client_cert. El certificado del usuario no llega a CERTRULE.
Respuesta final 401 Basic HTTP/1.1 401 Unauthorized y www-authenticate: Basic. Al eliminarse el certificado, ABAP no puede autenticar por X.509 y cae a desafío Basic.

Lectura del Caso P000001 / FSOLER

Conclusión: el bloqueo no parece ser que P000001 no exista en SAP. En el trace, para FSOLER, el certificado que ABAP recibe como reenviado tiene CN=fsoler@ccu.cl.

La regla CERTRULE vista durante la revisión toma Asunto / CN y entra al sistema con Correo electrónico. Por lo tanto, si el usuario SAP FSOLER tiene mantenido en SU01 el correo fsoler@ccu.cl, el mapping debería resolver una vez que ABAP acepte el certificado reenviado.

Elemento Valor observado Significado
Usuario en JWT / SCC monitor P000001 Identidad IAS/AD o atributo de login mostrado por SCC.
Email en JWT fsoler@ccu.cl Atributo que SCC usa para generar el CN del certificado de usuario.
Certificado reenviado CN=fsoler@ccu.cl Dato que CERTRULE usa para buscar usuario SAP por correo.
Usuario SAP esperado FSOLER Debe existir en SU01, estar activo y tener correo único fsoler@ccu.cl.

Qué Debe Implementar Basis

  1. Identificar el certificado de sistema del Cloud Connector que se usa para autenticarse frente al backend ABAP. No es el certificado de usuario CN=fsoler@ccu.cl; es el certificado del proxy/SCC.
  2. Importar en STRUST la CA/cadena que firma ese certificado de sistema del SCC. Validar el PSE asociado al puerto HTTPS 44300, por ejemplo SSL server Standard o el PSE indicado por el perfil/trace.
  3. Configurar el reverse proxy confiable en el perfil de instancia ABAP, usando el subject e issuer del certificado de sistema del SCC.
  4. Verificar que el puerto HTTPS donde entra SCC solicite certificado cliente. En el trace se observó PORT=44300, PROT=HTTPS, VCLIENT=1, lo que indica solicitud opcional de certificado; debe mantenerse alineado con la política del sistema.
  5. Reiniciar ICM con SMICM -> Administration -> ICM -> Restart -> Soft o aplicar el procedimiento Basis equivalente.
  6. Repetir la prueba y confirmar que el trace ya no muestre Reject untrusted forwarded certificate ni remove incoming ssl header.
  7. Validar CERTRULE y SU01: usuario FSOLER activo, correo fsoler@ccu.cl mantenido y sin duplicados.

Parámetro ICM Esperado

icm/trusted_reverse_proxy_0 = SUBJECT="<Subject DN del certificado de sistema del SCC>",
                              ISSUER="<Issuer DN de la CA que firma el certificado SCC>"

El subject/issuer debe corresponder al certificado del Cloud Connector como proxy, no al certificado del usuario final.

Checklist de Validación Posterior

Trace esperado
  • No aparece intermediary is NOT trusted.
  • No aparece remove incoming ssl header.
  • El certificado reenviado permanece disponible para autenticación.
Autenticación esperada
  • ABAP aplica CERTRULE.
  • CN=fsoler@ccu.cl resuelve al usuario SAP FSOLER.
  • El OData responde sin desafío Basic.

Notas de Aplicación

Durante la revisión también se observó que srv/handlers/s4-metadata.handler.js usa una destination hardcodeada S4H-TECH, mientras el cliente S/4 principal usa S4H-PP. Esto no cambia el hallazgo Basis del trace, pero puede confundir pruebas comparativas entre metadata y value helps.

El flujo de value helps como VH_DestMercBP termina llamando a S/4 vía SAP Cloud SDK con destination y principal propagation. La URL remota revisada fue:
