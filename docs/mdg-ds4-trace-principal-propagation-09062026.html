Diagnostico DS4 - Principal Propagation X.509

Revision del archivo trace ds4.xlsx para explicar por que el usuario es rechazado al invocar servicios OData en DS4 el 09 de junio de 2026.

Sistema: DS4 Cliente SAP: 120 Trace: dev_icm Fecha evento: 09-06-2026 Usuario observado: fsoler@ccu.cl

Resumen ejecutivo

El X.509 del usuario si llega a DS4.

El trace muestra el header ssl_client_cert y el certificado reenviado con subject CN=fsoler@ccu.cl.

DS4 no acepta ese certificado reenviado.

ICM indica que la conexion HTTPS real no trae certificado cliente del intermediario y por seguridad elimina los headers SSL.

Resultado visible para la aplicacion.

DS4 responde HTTP/1.1 401 Unauthorized en llamadas como ZCDS_CLIENTES_GEN_CDS/$metadata.

No parece un problema solo del usuario.

El mismo patron aparece para fsoler@ccu.cl y sergio.guaman@vacconsultores.cl, tanto el 01-06-2026 como el 09-06-2026.

Causa raiz probable: DS4 no tiene correctamente establecida la confianza del intermediario que reenvia el certificado X.509 por header. Para Principal Propagation HTTPS, SAP requiere que el backend acepte certificados reenviados solo desde proxies/intermediarios confiables.

Como debe funcionar

  1. La aplicacion en BTP llama a una destination con Authentication=PrincipalPropagation.
  2. El Connectivity Service y SAP Cloud Connector generan/propagan una identidad X.509 corta para el usuario autenticado.
  3. Cloud Connector accede al backend DS4 por HTTPS y reenvia el certificado del usuario en headers SSL.
  4. DS4 solo debe aceptar esos headers si el intermediario que los envia esta autenticado y configurado como proxy confiable.
  5. Cuando DS4 confia en el intermediario, el certificado reenviado puede llegar al mecanismo de logon X.509 de ABAP y mapearse al usuario SAP.
Punto exacto donde falla ahora: el paso 4. DS4 ve el header del certificado de usuario, pero no confia en el intermediario porque la conexion HTTPS no trae certificado cliente del proxy, o ese certificado no esta declarado como reverse proxy confiable.

Paso a paso para corregirlo

1. Confirmar la ruta tecnica del flujo

  • Identificar si la llamada va BTP -> Connectivity Service -> Cloud Connector -> DS4 directo, o si existe un SAP Web Dispatcher / balanceador entre Cloud Connector y DS4.
  • El componente que se conecta directamente a DS4 es el que DS4 debe reconocer como reverse proxy confiable.
  • En el trace aparece el host v-vhccuds4ci.sap.ccu.cl:44300 y user-agent axios/1.13.5.

2. Revisar Cloud Connector

  • En el mapping del sistema DS4, verificar que el protocolo sea HTTPS si se usara Principal Propagation X.509.
  • Activar Allow Principal Propagation.
  • Configurar Principal Type = X.509 Certificate.
  • Seleccionar/usar el System Certificate del Cloud Connector para la conexion hacia el backend.
  • Exportar el certificado de sistema de Cloud Connector y su cadena emisora si aplica.

3. Importar la confianza en DS4

  • En DS4, entrar a STRUST.
  • Importar el certificado cliente del intermediario, normalmente el certificado de sistema de Cloud Connector, en el PSE que atiende HTTPS del ICM. En este trace se ve /usr/sap/DS4/D00/sec/SAPSSLS.pse.
  • Importar tambien la cadena CA necesaria para validar el certificado del intermediario.
  • Guardar/distribuir el PSE segun la practica Basis del landscape.

4. Declarar el intermediario como reverse proxy confiable

Configurar en el perfil de DS4 un parametro vectorial icm/trusted_reverse_proxy_<n> usando el Subject y Issuer del certificado del intermediario, no el certificado del usuario final.

# Ejemplo conceptual. Los valores reales deben salir del certificado del Cloud Connector
# o del SAP Web Dispatcher/balanceador que conecta directamente contra DS4.
icm/trusted_reverse_proxy_0 =
  SUBJECT="CN=<certificado-del-intermediario>, ..."
  ISSUER="CN=<CA-emisora-del-intermediario>, ..."
Importante: no usar aqui CN=fsoler@ccu.cl. Ese es el certificado del usuario propagado. El parametro debe identificar al proxy/intermediario autorizado para reenviar certificados.

5. Reiniciar o recargar ICM segun ventana Basis

  • Aplicar el cambio de perfil segun el procedimiento de Basis.
  • Reiniciar ICM / instancia si el parametro no queda activo dinamicamente en el release correspondiente.
  • Repetir la llamada a /sap/opu/odata/sap/ZCDS_CLIENTES_GEN_CDS/$metadata por la misma destination con Principal Propagation.

6. Validar el nuevo trace

  • Ya no debe aparecer intermediary is NOT trusted.
  • Ya no debe aparecer Reject untrusted forwarded certificate.
  • No debe eliminarse el header SSL con remove incoming ssl header.
  • La respuesta esperada para metadata debe dejar de ser 401 Unauthorized.

7. Si despues aparece otro 401

  • Revisar mapeo de certificado a usuario ABAP, por ejemplo reglas de X.509 / CERTRULE segun la configuracion del sistema.
  • Verificar que el usuario SAP asociado exista, este desbloqueado y tenga autorizacion para el servicio OData.
  • Ese seria un segundo problema. El problema actual ocurre antes: DS4 descarta el certificado reenviado por falta de confianza del intermediario.

Documentacion SAP de respaldo

  • SAP Help - Principal Propagation : explica el concepto de reenviar la identidad del usuario cloud hacia un sistema remoto mediante Connectivity y Cloud Connector.
  • SAP Help - Configure Identity Propagation for HTTPS : indica que en el mapping de Cloud Connector se debe permitir Principal Propagation, elegir X.509 Certificate y usar System Certificate para HTTPS.
  • SAP Help - Set Up Trust for Principal Propagation : cubre el establecimiento de confianza necesario para Principal Propagation hacia sistemas on-premise.
  • SAP Help - Certificate Forwarding Security Considerations : documenta que los certificados reenviados deben aceptarse solo desde reverse proxies confiables.
  • SAP Help - icm/trusted_reverse_proxy_<xx> : referencia del parametro ICM para declarar reverse proxies confiables.
  • SAP Help - icm/HTTPS/trust_client_with_issuer : documenta parametros historicos para subject/issuer del reverse proxy confiable en escenarios ICM/Web Dispatcher.
  • SAP Help - icm/accept_forwarded_cert_via_http : referencia de seguridad sobre aceptacion de certificados reenviados por HTTP. Para este caso la recomendacion es mantener HTTPS y confiar solo en el intermediario correcto.
  • SAP KBA 3017609 - Reject untrusted forwarded certificate : KBA especifica para el sintoma observado en el trace. Puede requerir usuario S-user.
  • SAP KBA 3371621 - Common mistakes when setting ICM parameters : KBA sobre errores comunes al configurar parametros ICM para Cloud Connector, SCC y backend ABAP. Puede requerir usuario S-user.

Conclusion

El certificado X.509 del usuario si se genera y llega hasta DS4. La falla esta en la confianza del intermediario que lo reenvia. Para resolverlo, DS4 debe confiar en el certificado cliente del Cloud Connector/Web Dispatcher/balanceador que conecta directamente contra ICM y debe declararlo como reverse proxy confiable mediante la configuracion ICM correspondiente.
